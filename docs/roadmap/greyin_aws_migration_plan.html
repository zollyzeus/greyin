Revised verdict · 2026-08-31

Greyin’s path to AWS

Don’t move yet. Greyin is pre-revenue, has zero real users on prod, and its single self-managed VPS has held up under every real load this session has thrown at it (166+ e2e runs, no infra failure). A hyperscaler move right now trades a working ~$30/mo box for a realistic $150–250/mo floor and a real jump in operational surface (VPC, IAM, ECS, secrets, CI/CD) to solve a scaling problem that doesn’t exist yet. The architecture already in place — Postgres + RLS, containerized apps — is exactly what keeps this option cheap to exercise later; waiting doesn’t cost you the option. Below: why, the cheaper middle step if partial reliability is wanted sooner, the concrete triggers that should flip this call, and — once one fires — the path this page originally laid out.

Should Greyin move to a hyperscaler at all, right now?

No. Not because the architecture wouldn’t survive it — it would — but because nothing today needs it, and the cost of finding out is real money at a stage where every dollar is runway.

No revenue, no usersProd has never carried a real end user. There is no uptime SLA to meet, no traffic pattern to absorb, no customer asking for it. Migrating now optimizes for a load profile that doesn’t exist.
The VPS hasn’t actually failedOne node has carried this session’s entire e2e history — 166+ tests in a single run, repeated full-suite passes — with zero infra-caused outage. The evidence for “this can’t scale” doesn’t exist yet; the evidence for “this has held up fine” does.
Real cost jumpRough floor, not a quote: Supabase Cloud Pro ~$25 + Fargate compute for 6 apps ~$60 + ALB ~$20 + NAT Gateway ~$35 (a fixed hourly charge regardless of traffic) + CloudFront/Route 53/Secrets Manager ~$10–15 ≈ $150–250/mo, against a current all-in ~$24–40/mo. That’s 5–8×, mostly in charges that don’t scale down to zero even at zero traffic.
Opportunity costThe audit two passes back found 13 real functional gaps (self-service job close/reopen, OAuth, feedback loop, pre-publish moderation) that move Greyin toward actually having users. At MVP stage, that’s very likely the higher-value use of the same engineering hours.
Optionality isn’t decayingBecause the app already speaks Postgres + RLS through a portable client shape, this option stays just as cheap to exercise in six months as it is today. Nothing about waiting locks anything in — the opposite of, say, building on Emergent’s proprietary object-storage API, which does get more expensive to leave the longer it’s used.

If partial reliability is wanted sooner, there’s a cheaper middle step

The full plan below bundles two separate decisions — “do I want managed, multi-AZ Postgres” and “do I want a full hyperscaler re-architecture” — that don’t have to move together.

DoMove just the database to Supabase Cloud (~$25/mo to start) if the single point of failure on Postgres specifically is the actual worry — same client calls, same RLS, a pg_dump/restore away.
Don’t (yet)Leave the 6 Next.js apps exactly where they are, or at most move them to a lightweight PaaS (Fly.io, Render, Railway) if the VPS itself becomes the concern — a fraction of ECS/VPC/ALB’s operational weight for a team this size.

Is this even an AWS-specific decision?

Mostly no — worth naming since the previous pass framed this as “AWS” specifically. The one concrete thing pulling toward AWS was “Supabase Cloud happens to run on AWS,” but the app never talks to an AWS API directly through that path — it talks to a Supabase endpoint. Supabase Cloud project region/provider is a setting, not an architectural commitment. This only becomes a real AWS-vs-GCP-vs-Azure decision the day something in the stack starts calling a hyperscaler’s native APIs directly (Lambda, native S3, SES) — not before.

Triggers that should flip this recommendation

Revisit this page when any one of these is true, not on a calendar.

→

Real paying customers with an uptime expectation

A revenue commitment changes what an outage costs — that’s the actual trigger for HA, not the architecture diagram existing.

→

The VPS actually runs out of headroom

CPU/RAM/disk pressure under real (not test) load — measured, not guessed.

→

A customer or compliance ask specifically requires it

An enterprise buyer needing SOC2/a named cloud provider is a real, external forcing function — very different from a self-imposed one.

Today vs. the recommended target — once one of the triggers above fires

What changes is everything below the Supabase client URL. What doesn’t change is every line of app code that calls it.

single point of failure today managed / auto-scaling / multi-AZ the unchanged contract

Get there in five steps, not one leap

For when a trigger above actually fires. Each step ships independently and de-risks the next one. Nothing here requires an app-code rewrite.

What this deliberately does not do

KeepEvery RLS policy, every Supabase client call, every migration file — all 86 of them apply to Supabase Cloud unchanged.
ChangeOnly the hosting substrate: one VPS → managed multi-AZ services. The app never notices.
RejectedFull decompose to RDS + Cognito + native S3 SDK. Technically possible, but rewrites the auth/RLS layer for no functional gain — the coupling to Supabase’s JWT shape makes this the expensive path, not the natural one.

Gaps in this plan, before it’s executable

For whenever a trigger fires — the five steps above are the right order, but not yet a runbook. Each of the following needs an answer first, ranked by what actually blocks starting vs. what just needs a decision on record.

01

Cost estimate is order-of-magnitude, not a quote

blocker

The $150–250/mo figure above is built from known fixed-charge line items (ALB, NAT Gateway), not a real AWS pricing calculator run or a Supabase Cloud usage projection. Good enough to see the shape of the decision now; not good enough to budget against — get a real number before the day this is actually triggered.

02

No cutover runbook

blocker

Step 2 says “pg_dump → restore, swap URL + keys” as if it’s one motion. It isn’t: what freezes writes during the dump, how long is that window, what’s the DNS TTL before traffic actually follows the cutover, and what’s the fallback if Supabase Cloud misbehaves in the first hour — flip Route 53 back to the still-warm VPS, or fix forward? None of that is decided yet.

03

“Test against prod only” has no answer for a substrate migration

blocker

The project’s own standing convention is e2e runs against real prod, not an isolated stack. That convention has no meaning for a migration that, by definition, doesn’t have a “prod” on the new substrate yet. This plan needs an explicit, named exception — e.g. running the full e2e suite against the new AWS stack before it takes real traffic, once only — rather than silently skipping validation or silently breaking the existing rule.

04

Secrets management unaddressed

needs a decision

Every credential (JWT_SECRET, DB passwords, Razorpay keys, LLM provider keys) currently lives in a plain .env file on the VPS — the exact shape of thing this session’s own JWT rotation had to work around. ECS task definitions want these injected from Secrets Manager or SSM Parameter Store, not baked into an image or a compose file. Worth doing as part of step 3, not left implicit.

05

No VPC/network design

needs a decision

“ECS Fargate” isn’t a complete answer by itself — it needs subnets (public for the ALB, private for the tasks), security groups scoped to only what talks to what, and a NAT gateway for the apps’ outbound calls (Supabase Cloud, Razorpay, the LLM providers). Undrawn in the diagram on purpose — it’s a real step 3 sub-task, not a detail to skip.

06

Kong config carryover unverified

needs a decision

The current stack has hand-signed consumer JWTs in kong.yml from this session’s own SEC-011 rotation work. Supabase Cloud runs its own managed gateway — worth explicitly confirming there’s no custom Kong routing/plugin this project depends on beyond stock Supabase behavior, rather than assuming a clean swap.

07

Bundle the parked SES fix into this same migration

worth bundling

Hostinger’s 500/hr SMTP cap is a known, already-parked issue (session memory: project_smtp_rate_limit_parked.md), with SES already on record as the recommended fix. An AWS migration is the natural moment to fold that in rather than carry the SMTP limitation onto the new infra unchanged.

08

No observability plan

oversight

Nothing here says how you’d know a Fargate task is unhealthy or Supabase Cloud is degraded — ECS health checks, CloudWatch log groups/alarms, and a real on-call signal need to exist before this carries production traffic, not get added after the first incident.

09

Region alignment + version parity unverified

oversight

The Supabase Cloud project region needs to match the ECS region (cross-region DB calls would quietly add latency to every request). And this session has already hit real version-mismatch bugs more than once (the @supabase/ssr cookie-format break, the PostgREST schema-cache-reload gotcha) — worth explicitly confirming Supabase Cloud runs the same Postgres extensions and PostgREST/GoTrue versions as the self-hosted stack before assuming the migrations apply cleanly.

10

No CI/CD path stated

oversight

Deploys today are a manual shell script (deploy.sh, docker stack deploy). Step 3 implicitly assumes images land in ECR and task definitions update somehow — that pipeline (GitHub Actions or CodeBuild/CodePipeline) isn’t designed yet, just presumed.
