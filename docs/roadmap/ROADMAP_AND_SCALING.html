Executive Summary

Greyin has shipped 110+ features across 6 pillar apps and a unified Hub with production-ready infrastructure (self-hosted Supabase, Docker Swarm, Kong gateway, Traefik reverse proxy). This roadmap addresses three parallel tracks:

🚀 UI/UX Excellence

Shipped: Workspace shell (persistent rail + top bar), notification unification, guided tour, command palette, in-context feedback.

Target: ≥8/10 on UX dimensions (from current ~7.2/10).

📊 Parked Features (Known Gaps)

9 planned features deferred or blocked: advanced search NL filters, salary dashboard, peer verification batching, AI quality assist, revenue dashboard, admin analytics, role-based access control (RBAC), mobile app, and custom integrations.

Reason: Prioritized UI/UX completion, operational stability, team capacity.

📈 Scaling (10K → 100K users)

Planned: Database sharding, read replicas, CDN caching, LLM cost optimization, multi-region deployment.

Trigger: User growth thresholds, performance degradation, cost efficiency targets.

Parked & Pending Features

Status: 9 planned features are PARKED or BLOCKED. These were designed, scoped, and prioritized but deferred to make room for UI/UX completion and operational stability. Re-activation depends on user demand, team capacity, or business impact.

High-Priority Parked Features (Reactivate: Q1 2027)

1. Advanced Search NL Filters (DeepEdge)

PARKED HIGH

Description: Natural language filters like "show me jobs that pay $150–200K in NYC, remote-ok, hiring now." Uses the existing LLM intent classifier to parse queries into structured filters before querying jobs table.

Current: Simple keyword search only. Advanced filters exist on the page but rarely used.

Why Parked: LLM call per search + cost tracking overhead. Competing with post-quality and resume-parsing LLM budget.

Acceptance Criteria: NL query like "remote python senior NYC 150-200k" returns 5+ matching jobs; accuracy ≥85% vs. manual tag filters.

Estimated Effort: 5 days (backend prompt tuning, frontend integration, e2e testing).

2. Salary Analytics Dashboard

PARKED HIGH

Description: A new "Salary Insights" page (on DeepEdge) showing trends by role, location, company, seniority. Uses salary_trends materialized view with k-anonymity ≥3.

Current: No dashboard; data exists in the view but inaccessible to users.

Why Parked: Requires charting library (recharts), design pass, and permission model (which employers can see which salary ranges?).

Acceptance Criteria: View "Senior Engineer" salaries in NYC (30 data points), grouped by company size, with 25th/50th/75th percentiles.

Estimated Effort: 3 days (design + recharts integration).

3. Peer Verification Batching (StackWorks)

PARKED HIGH

Description: Collect peer signatures before marking a project outcome as verified. Right now, one peer's vote is enough (trust-through-low-bar). Batch verification requires 2–3 peer confirmations (configurable by platform).

Current: Single-peer voting works; fraud-flag logic detects obvious collusion but doesn't block.

Why Parked: Affects outcome-score calculation, requires migration of existing outcomes, needs UX for review queues.

Acceptance Criteria: New projects await 2/3 peer approvals before verification badge appears. Admin can raise threshold per pillar.

Estimated Effort: 1 week (schema migration, workflow UI, admin panel).

Medium-Priority Parked Features (Reactivate: Q2 2027)

4. Gig Quality AI Assist (FlexPro)

PARKED MEDIUM

Description: When a freelancer creates a gig listing, LLM suggests improvements: "Title too generic, try 'end-to-end React 19 app setup'"; "Rate is below market for this skill, consider $75–100/hr".

Current: Post-quality gate exists but only for Salt & Pepper discussions.

Why Parked: Requires market-data model (what rate ranges are current?) and a separate LLM prompt tuned for gig quality vs. post quality.

Acceptance Criteria: Freelancer sees 3–5 actionable suggestions as they create a gig; can dismiss or apply them.

Estimated Effort: 4 days (prompt engineering + frontend modal).

5. Admin Revenue Dashboard

PARKED MEDIUM

Description: Greyin's revenue by source (DeepEdge subscriptions, FlexPro mentor premiums, platform fees). Tracks recurring vs. one-time, MRR, churn rate, LTV per pillar.

Current: Raw Razorpay API calls work, but no aggregated view. Admin must query manually or export CSVs.

Why Parked: Needs analytics infrastructure (event logging already shipped in Phase 6); requires charting + finance data model.

Acceptance Criteria: Dashboard shows MTD revenue by pillar, MRR, projected annual recurring revenue (ARR), churn rate trending.

Estimated Effort: 4 days (analytics queries, recharts).

6. User Analytics Dashboard

PARKED MEDIUM

Description: Admin view of engagement metrics: DAU/MAU, onboarding completion rate, feature adoption (who uses command palette, guided tour), pillar-switch rate.

Current: Events table exists; no dashboard. Admin can query SQL directly.

Why Parked: Requires dashboard UI + design; analytics already logged (Phase 6).

Acceptance Criteria: View last 7/30 days DAU/MAU, onboarding completion rate (%), guided tour replay clicks, pillar hops/user/day.

Estimated Effort: 3 days (dashboard page + recharts).

Low-Priority / Future Parked Features (Q3 2027+)

7. Role-Based Access Control (RBAC)

PARKED LOW

Description: Formalize permissions beyond simple admin/user. Examples: "Content Moderator" (read + moderate discussions, but no access to payments), "Hiring Manager" (post jobs + review candidates, no access to platform analytics).

Current: Only role='admin' vs. role='user'. Admin is all-or-nothing.

Why Parked: Scope creep risk; current binary role is sufficient for 10K users. Migration path documented in ADR-013.

Acceptance Criteria: Define 5–8 roles (Admin, Moderator, Analyst, Support, Employer, etc.). Implement one role (e.g., Moderator) as a proof-of-concept.

Estimated Effort: 2 weeks (schema migration, RLS policy rewrite, admin UI).

8. Native Mobile Apps (iOS/Android)

PARKED LOW

Description: React Native apps for iOS and Android, sharing 70–80% codebase with the web frontend.

Current: Web-responsive apps work on mobile but not app-store-ready (no push notifications, no offline sync, no in-app payment routing).

Why Parked: Requires dedicated mobile team; web-responsive MVP sufficient for 2026–2027.

Acceptance Criteria: Fully functional iOS/Android versions in app stores, push notification delivery, offline job search caching (StackWorks).

Estimated Effort: 8–10 weeks (two developers, Expo + Firebase Cloud Messaging).

9. Custom Integrations & API Webhooks

PARKED LOW

Description: Let third parties build integrations: "When a job is posted on DeepEdge, send a webhook to our ATS," or "Sync Greyin candidates to our hiring platform."

Current: PostgREST API exists but no webhook infrastructure, no API key management, no rate limiting per customer.

Why Parked: Requires developer portal, documentation, support infrastructure. Deferred until 10K+ users and real demand.

Acceptance Criteria: Admin can create API keys, set rate limits, register webhook endpoints. Webhooks fire for job_posted, candidate_applied, outcome_verified events.

Estimated Effort: 2 weeks (webhook service, developer portal, documentation).

Known Risks & Mitigations

Risk 1: Database Query Bottleneck (Greyin Score, Search)

Impact: At 10K concurrent users, unoptimized queries on greyin_scores / platform_search_index could timeout. Dashboard loads >5s.

Mitigation: Phase A includes indexing pass + Redis cache; Phase B includes read replicas + query routing.

Timeline: Monitoring + alerting in place now; proactive indexing by Oct 2026.

Risk 2: LLM Provider Cost Explosion

Impact: Unexpected LLM usage surge (e.g., a feature accidentally logs every page load) could push costs to $1K+/mo.

Mitigation: Feature flags per LLM call; cost tracking in llm_requests table; admin dashboard with spend alerts. Feature can be toggled off in <5 min.

Timeline: Alerts configured by Nov 2026.

Risk 3: Cross-Domain Auth Desync

Impact: If JWT refresh token (shared on .greyin.net domain) expires, user logged out of all 6 apps simultaneously. Poor UX if refresh fails.

Mitigation: Refresh token expires in 400 days; clients refresh proactively (before expiry). 2-minute warning before force-logout (ADR-011).

Timeline: Tested in Phase 1 (idle timeout acceptance spec); live monitoring by Dec 2026.

Risk 4: Mobile Validation Gap

Impact: Workspace shell designed for desktop; 375px mobile breakpoint may have rendering bugs or UX friction.

Mitigation: Full mobile screenshot pass (Q4 2026, Phase 1). Deployment hold until mobile tests pass.

Timeline: Validation by end of Nov 2026.

Risk 5: Realtime Notification Failures

Impact: If Supabase Realtime WebSocket connection drops, users don't see live job alerts / messages until next page reload.

Mitigation: 30-second polling fallback (already live); Realtime reconnection on page-visibility change. Acceptance test in Phase 2.

Timeline: Fallback operational; enhanced reconnection logic by Dec 2026.

Risk 6: Session Cookie Not httpOnly (SEC-016)

Impact: Session cookies across all 6 apps carry secure/sameSite:'lax' but deliberately not httpOnly — a real, unmitigated XSS on any one app can read the session cookie directly. Found in the 2026-08-24 security audit; the traceability matrix's own status field says "Fixed," which overstates it (that column reflects the secure/sameSite work; httpOnly itself was a deliberate, separately-tracked gap from day one).

Mitigation: Every app's SiteHeader.tsx calls createClient().auth.getUser() client-side to decide Sign-In-vs-logged-in display; an httpOnly cookie is invisible to that call and would break login-state display platform-wide as-is. Closing this for real needs a genuine refactor — moving that check to a server-rendered prop across all 6 apps — not a cookie-flag change.

Timeline: Not scheduled; revisit alongside any broader auth/session refactor, since it's not a standalone flag flip.

Contingencies & Escape Hatches

If user growth stalls (DAU plateaus <300 by end of Q4 2026):
  • Pause scaling roadmap (Phase B). Maintain Phase A optimization for operational health.
  • Redirect team to parked features (advanced search, salary dashboard) to increase engagement.
  • Conduct user research (cohort interviews) to identify friction points.
  • Re-evaluate product-market fit; consider pivot to specific use case (e.g., "hiring platform for remote-first companies" vs. broad "professional community").
If infrastructure costs exceed $600/mo before 5K users:
  • Pause Redis cache expansion. Use Supabase materialized view caching only.
  • Disable LLM features (post quality, recommendations) that don't directly drive revenue.
  • Evaluate managed Supabase SaaS vs. self-hosted (trade operational burden for cost predictability).
If mobile validation finds critical UX issues (>30% task failure rate at 375px):
  • Extend Q4 mobile work into early Q1 2027.
  • Defer performance optimization (Phase A) by 4 weeks; prioritize UX fixes.
  • Consider web-responsive MVP acceptable for 2026; native mobile apps as separate Phase (2027 H2).
If database sharding (Phase B) exceeds 3 weeks effort estimate:
  • Pause sharding. Use vertical scaling (larger Postgres instance) as interim solution.
  • Consider Managed PostgreSQL (AWS RDS, Heroku Postgres) instead of self-hosted to shift operational burden.
  • Re-estimate sharding as 2027 Q3+ work.

Consolidated Timeline

Conclusion

Greyin has achieved feature completion for an MVP platform with 110+ features, 6 pillar apps, unified SSO, and real-time notifications. The Q4 2026 roadmap focuses on mobile validation and performance optimization to support 10K concurrent users, while 9 parked features remain candidates for re-activation based on user demand and business impact.

The scaling plan (Phase B, Q1–Q2 2027) enables 100K+ active users via database sharding, multi-region deployment, and cost optimization. Infrastructure costs remain predictable: ~$1.1–1.6K/mo at 100K users (excluding payment processor fees).

Success depends on: (1) mobile validation passing Q4 2026, (2) user growth achieving 500–800 DAU by year-end, and (3) operational efficiency targets (sub-100ms query latency, $100–150/mo LLM spend). Contingencies are in place for slower growth, cost overruns, or platform bottlenecks.
