Introduction

This document captures the major architectural decisions made during Greyin platform development, including rationale, alternatives considered, and trade-offs. Each decision is organized as an Architecture Decision Record (ADR).

ADR-001: Supabase Self-Hosted vs. Commercial PaaS

DECISION: Self-Hosted Supabase
Rationale:
  • Cost: $27-42/month vs. $500-2000/month SaaS alternatives (5-year TCO: $80K vs. $145K+)
  • Lock-in: Open source components (LGPL v3, GPL v2, Apache 2.0) enable exit
  • Control: Full database access for complex queries, triggers, RLS
  • Scale: Can handle 1000+ concurrent users on $24/mo VPS
  • Vendor Risk: No single vendor controlling user data
Alternatives Considered:
  • Firebase (Firestore): No complex SQL, limited RLS, vendor lock-in
  • Directus: Headless CMS focused, not ideal for StackWorks/FlexPro business logic
  • PocketBase: Single-file SQLite, insufficient for 100+ concurrent users
  • Frappe/ERPNext: ERP focused, heavyweight for marketplace platform
✗ Trade-offs (Cons):
  • Operational overhead: manual upgrades, backup management, monitoring
  • DevOps skill requirement (Docker, PostgreSQL, Kong configuration)
✓ Trade-offs (Pros):
  • Unlimited SQL complexity and custom functions
  • Transparent cost per feature (can see LLM spend, storage usage)

ADR-002: 6-Pillar Microapp Architecture vs. Monolith

DECISION: Separate Next.js Apps
Rationale:
  • Independent Deployment: Each app can ship features on its own cadence (no blocking)
  • Isolated State: Apps can be deleted/paused without affecting others (e.g., pause GreyMatters, keep others live)
  • Distinct UX: Each app can optimize UI for its specific workflow (job search ≠ forum discussion)
  • Team Scaling: Multiple teams can own separate pillars without coordination overhead
  • Skill Variety: Recruit engineers with deep expertise in marketplace (FlexPro), community (Salt & Pepper), etc.
✗ Trade-offs (Cons):
  • Code duplication risk: each app has its own SiteHeader (mitigated by shared git discipline)
  • Deployment coordination: 7 apps to deploy, not 1
✓ Trade-offs (Pros):
  • Clear boundaries: DeepEdge team owns /candidates/[id], no conflicts
  • Fast development: feature ship → test → deploy in parallel

ADR-003: Greyin Score — Bayesian Shrinkage vs. Simple Average

DECISION: Bayesian Shrinkage
Rationale:
  • Noisy Signal Reduction: A user with 1 outcome scoring 95/100 doesn't deserve 95 points (could be outlier)
  • Shrinkage Formula: Pulls high-outlier scores down, low-outlier scores up toward population mean
  • Headcount Weight: More outcomes = less shrinkage = more weight to actual performance
  • Fairness: A candidate with 10 outcomes at 70 is more trustworthy than one with 1 outcome at 100
def shrink_toward_mean(observed_mean, population_mean, n, precision): # Bayesian posterior: blend observed data with population knowledge # Higher n (more outcomes) → less shrinkage # Lower n (rare outcomes) → strong shrinkage toward mean weight = n / (n + precision) shrunk_score = weight * observed_mean + (1 - weight) * population_mean return shrunk_score # Example: 1 outcome at 95 vs. 10 outcomes at 70 single_outcome = shrink_toward_mean(95, 40, 1, 10) # → ~50 (shrunk down) many_outcomes = shrink_toward_mean(70, 40, 10, 10) # → 65 (less shrinkage)
✗ Trade-offs (Cons):
  • Harder to explain to users (Bayesian statistics)
  • Score may feel low to high-performing early users
✓ Trade-offs (Pros):
  • Resistant to gaming/sockpuppeting
  • Score improves as users build history (incentivizes long-term engagement)

ADR-004: Row-Level Security (RLS) vs. Application-Layer Authorization

DECISION: Database-Layer RLS
Rationale:
  • Unhackable by App Bug: An RLS bug in auth.ts can't bypass database policy
  • Audit Trail: Every SELECT/UPDATE logged by PostgreSQL, not buried in app logs
  • Scaling: Authorization logic doesn't scale with N apps (all 6 pillars obey same RLS)
  • Consistency: No chance of DeepEdge implementing permission check differently from FlexPro
-- Every user-scoped table has policy like: ALTER TABLE applications ENABLE ROW LEVEL SECURITY; CREATE POLICY "Users can read own applications" ON applications FOR SELECT USING (auth.uid() = candidate_id OR auth.uid() IN ( SELECT owner_id FROM companies WHERE id = job_id::company_id )); -- Even if app accidentally queries all applications, -- database filters result set automatically
✗ Trade-offs (Cons):
  • RLS policies harder to debug (not in IDE syntax highlighting)
  • Requires SQL knowledge to understand policies
✓ Trade-offs (Pros):
  • No way to accidentally expose data via app bug
  • Admin can query logs and see if RLS was ever bypassed

ADR-005: Synchronous LLM Scoring vs. Async Job Queue

DECISION: Hybrid (Sync for user-facing, Async for batch)
Rationale:
  • User Feedback: Resume parsing blocks upload completion, but users expect instant feedback
  • Cost Control: Async allows rate limiting (e.g., daily digest job runs once/day)
  • Fallback Path: If LLM provider down, upload still succeeds (quality missing, not blocked)
  • Simplicity Trade-off: Sync is simpler; async adds job queue burden
Feature Sync/Async Reason Latency
Resume parsing Sync (timeout 2s) Upload completion UX <2s
Post quality Sync (blocking gate) Pre-publish QA <2s
Outcome verification Sync (creator review) Happens during human review <3s
Gig quality assist Sync (suggestions) Non-blocking, seller sees immediately <1s
Digests Async (nightly) Batch operation —
Salary trends Async (hourly) Pre-computed materialized view —
✗ Trade-offs (Cons):
  • Sync calls can timeout (handled via try/catch, degrades gracefully)
  • Cost spike if LLM provider fails to rate-limit (mitigated by admin flags)
✓ Trade-offs (Pros):
  • Immediate user feedback for upload completion
  • Batch operations keep costs low

ADR-006: Shared Cookie Domain (SSO) vs. Per-App Logins

DECISION: Shared .greyin.net Cookie Domain
Rationale:
  • User Friction: Login once → access all 6 apps without re-authenticating
  • Token Refresh: All apps share same JWT refresh token cookie, no desync
  • Real-World Usage: Users switch between apps during sessions (e.g., post StackWorks, share on GreyMatters)
Cookie: __Secure-sb-access-token Domain: .greyin.net # Shared across all subdomains Path: / HttpOnly: true # Inaccessible to JavaScript Secure: true # HTTPS only SameSite: Lax # CSRF protection Max-Age: 3600 # 1 hour Refresh Token: Domain: .greyin.net Max-Age: 34560000 # 400 days
✗ Trade-offs (Cons):
  • If one app logs you out, all apps log you out (intentional security feature)
  • Cookie theft = access to all 6 apps (mitigated by httpOnly + secure flags)
✓ Trade-offs (Pros):
  • No session desync between apps
  • True unified platform experience

ADR-007: Materialized Views for Greyin Score vs. Real-Time Calculation

DECISION: Materialized View (Hourly Refresh)
Rationale:
  • Query Speed: Pre-computed score responds in <100ms (vs. 5+ second calculation)
  • Consistency: All views of a user's score within an hour are identical (no race conditions)
  • LLM Cost: Score doesn't invoke LLM (would be expensive per-request)
  • Admin Insight: View includes debugging columns (per-platform breakdowns)
-- Refresh materialized view every hour via pg_cron SELECT cron.schedule( 'refresh_greyin_scores', '0 * * * *', -- every hour 'REFRESH MATERIALIZED VIEW CONCURRENTLY greyin_scores' ); -- Result: 95 tables → view queries in parallel → merged result -- Concurrency prevents long-term locks
✗ Trade-offs (Cons):
  • Score lags real activity by up to 1 hour
  • Requires pg_cron for refresh (adds operational complexity)
✓ Trade-offs (Pros):
  • Fast profile page loads
  • Employers can search by score without slow queries

ADR-008: k-Anonymity for Salary Trends vs. Raw Aggregates

DECISION: k-Anonymity (k≥3)
Rationale:
  • Privacy: With only 2 salaries at "Senior Engineer, NYC", you can identify individuals
  • Business Confidence: Employers trust aggregates based on 10+ samples vs. 2
  • Regulatory: GDPR/privacy regulations expect k-anonymity on demographic data
  • Transparency: Users know aggregates are robust (3+ samples shown in UI)
-- Only show aggregates with k≥3 CREATE VIEW salary_trends AS SELECT role_level, location, years_experience, AVG(salary_usd) as avg_salary, PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY salary_usd) as q1, PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY salary_usd) as q3, COUNT(*) as sample_size FROM employment_history WHERE years_experience >= 10 GROUP BY role_level, location, years_experience HAVING COUNT(*) >= 3; -- k-anonymity threshold
✗ Trade-offs (Cons):
  • Early platform has gaps (rare job titles below k=3 threshold)
  • Requires tracking salary submissions (privacy risk if breached)
✓ Trade-offs (Pros):
  • Candidates trust salary data as representative
  • No way to reverse-engineer individual salaries

ADR-009: LLM Provider Registry vs. Hardcoded Provider

DECISION: Pluggable Provider Registry
Rationale:
  • Vendor Optionality: If Anthropic prices spike, switch to OpenAI
  • Cost Optimization: Route different features to different providers (fast features → cheaper model)
  • Local Inference: Support Ollama for on-premise deployments
  • Feature Flags: Admin can disable a feature's LLM scoring (e.g., disable post quality if budget tight)
Provider Model Cost (1K tokens) Use Case
Anthropic claude-3.5-sonnet $0.003 in / $0.015 out High-quality scoring, verification
OpenAI gpt-4 $0.03 in / $0.06 out Complex reasoning (fallback)
OpenAI gpt-3.5-turbo $0.0005 in / $0.0015 out Budget mode, simple tasks
Ollama llama2, mistral $0 (self-hosted) On-premise deployments
✗ Trade-offs (Cons):
  • Admin overhead: configure providers, monitor costs, toggle flags
  • Latency variance (Ollama may be slower than API endpoints)
✓ Trade-offs (Pros):
  • Cost control and vendor independence
  • Can experiment with cheaper models for specific features

ADR-010: Peer-Confirmed Projects vs. Verification-Only Achievements

DECISION: Separate peer_score from greyin_score
Rationale:
  • Evidence Types: In-platform verified outcomes (StackWorks/FlexPro) are gold-standard; off-platform collaboration is weaker signal
  • Reciprocal Rating Fraud: Without gating, two friends could collude to rate each other 5 stars (detected via flags)
  • Transparency: Employers see both scores, can weight as they choose
  • Safety: Peer projects don't affect hiring (Verified Expert gate), only informational
✗ Trade-offs (Cons):
  • More complex scoring system (two separate scores, not one)
  • Harder to explain to users
✓ Trade-offs (Pros):
  • Resistant to gaming via collusion
  • Preserves integrity of StackWorks/FlexPro evidence

Additional Decisions (ADR-011 to ADR-014)

ADR-011: Idle Session Timeout

Decision: 20-minute idle + 2-minute warning

Rationale: Security (prevent unattended hijacking) + User control (warning allows recovery)

Pattern: AWS/Salesforce standard

ADR-012: Dark Mode Implementation

Decision: Tailwind dark:class + localStorage toggle + system preference fallback

Rationale: User choice (override system), no FOUC (inline script), persistent (localStorage)

Coverage: 240+ classes darkified across 7 apps

ADR-013: Explicit Admin Role

Decision: Simple role='admin' field vs. ABAC

Rationale: Simplicity (3 roles covers all use cases), RLS clarity, avoids over-engineering

Future Path: Can migrate to fine-grained permissions if needed via roles_pivot table

ADR-014: Test Data Cleanup

Decision: Synchronous admin-triggered cleanup route

Rationale: Simplicity (one-off), transparency (admin sees results), idempotence (can run multiple times)

Implementation: POST /api/admin/cleanup-test-data filters by "E2E " prefix

Architecture Philosophy

Simplicity Over Cleverness

Bayesian shrinkage is the most complex scoring algorithm; everything else is straightforward. Avoid over-engineering until it's clearly needed.

Database-Layer Security

RLS policies, not app-layer authorization. PostgreSQL enforces permissions regardless of app bugs.

Transparent Operations

Every LLM call logged, every cost attributed, every admin action auditable. Visibility builds confidence.

User Agency

Idle timeout warning (not forced), dark mode toggle (not system-only), feature flags (not hardcoded). Respect user choices.

Vendor Independence

Pluggable LLM providers, self-hosted Supabase, open source everywhere. Avoid lock-in; maintain exit strategies.

Privacy First

k-anonymity on salary, anonymous peer ratings, RLS everywhere. Default to privacy-preserving design.

Scalable Teams

6 pillar apps can ship independently, shared Hub enforces consistency. Structure enables team growth without chaos.

Conclusion

These 14 decisions prioritize long-term maintainability, security, and cost efficiency over short-term implementation speed. Each decision includes clear trade-offs, enabling future architects to understand when/if to reconsider.

As the platform grows, revisit these decisions annually. Market conditions change, technologies evolve, and the best decision today may need reconsideration tomorrow.
